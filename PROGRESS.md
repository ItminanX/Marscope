### Architecture (short)
`ingestion/pds3.py` (PDS3 label + raw IMG reader, validation, pixel-exact clip) → `scripts/build_region.py`
(slope / relief / hillshade on a sphere, derived rim target, layer PNGs, provenance) →
`data/processed/jezero/{grid.npz, manifest.json, layers/*.png}` → `store.py` + `routing/engine.py`
(cost model, A* on the native grid, segment evidence) + `briefing/brief.py` → FastAPI `main.py` (`/api/*`) →
React/Leaflet UI (CRS.Simple on the lat/lon grid). `scripts/build_snapshot.py` freezes API responses to
`frontend/public/demo/snapshot.json` for the no-backend mode.

### Data flow: raw tile → screen
`.lbl/.img` → parse + validate → clip ROI (no resampling) → slope/relief/hillshade → PNG overlays + `grid.npz`
→ Store loads grid → A* per mode → segments + evidence + brief → JSON → Leaflet overlays, WHY panel, brief.

### Risks
- **No real terrain:** all route numbers are synthetic → must be labelled everywhere (banner, chips, brief).
- **No FastAPI here:** add a Starlette fallback app (Starlette *is* installed) sharing the same handlers, so
  the API, tests and snapshot can run offline; FastAPI stays the primary server on a normal laptop.
- **No Vite/Leaflet here:** the UI must be rebuilt with esbuild + locally present React 19; Leaflet 1.9.4 can
  only be reused from the previous build's own bundle. TypeScript type-checking against real React/Leaflet types is
  not possible offline → keep the code conservative; `npm run build` on a laptop re-checks it.
- **Finer grids look sharper but contain no new information** → say so in the UI and docs.
